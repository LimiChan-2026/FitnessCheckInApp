## 一、需求分析

### 1.1 项目背景与目标

本项目面向「个人运动记录 + 好友监督激励」场景，构建一套移动互联系统。设计目标：

1. **易用**：打卡操作路径短，计时、记录、统计自动化；
2. **可靠**：弱网/断网不影响打卡，数据不丢失；
3. **互联**：多用户数据经服务端汇聚，支撑排行榜与好友互动；
4. **可验证**：以自动化测试与联调数据证明系统达到设计要求。

## 二、总体架构设计

### 2.1 系统架构（C/S + 离线优先）

```
┌────────────────────────── Android 客户端 ──────────────────────────┐
│  UI 层     Login/Register/ForgetPassword/Main/CheckIn/Data/Mine/Social │
│  业务层    Records/Stats/Social/Sync（打卡上云与离线降级）             │
│  网络层    ApiClient（HttpURLConnection + org.json，REST 封装）        │
│  本地层    SQLite（fitness_check_in.db：user_info / sport_record）     │
└───────────────────────────────┬────────────────────────────────────┘
                                │ HTTP + REST + JSON（UTF-8）
┌───────────────────────────────┴────────────────────────────────────┐
│                        Javalin 6 REST 服务端                        │
│  路由层    Main.java（/api/* 路由、异常统一处理）                    │
│  业务层    FitnessService（认证/记录/排行榜/动态/点赞/关注）          │
│  数据层    Database（sqlite-jdbc，参数化 SQL）                       │
│  存储      fitness_server.db（users/sport_records/likes/follows）    │
└────────────────────────────────────────────────────────────────────┘
```

设计原则：**本地 SQLite 是打卡数据的第一事实来源**（离线可用），服务端承担多用户共享数据（账号、云端记录、社交关系）。两者通过「本地先写、异步上云」解耦。

### 2.2 网络协议设计（REST + JSON）

**协议约定：**

- 传输层：HTTP/1.1，请求/响应体均为 JSON（UTF-8，服务端强制响应编码）；
- 业务约定：HTTP 2xx + `code==0` 表示成功；错误返回对应 HTTP 状态码（400/401/404/409/500）+ `{code, message}`；
- 数组型结果（feed/leaderboard/search）直接返回 JSON 数组；对象型结果返回顶层字段对象；
- 客户端超时：连接 5 s、读取 8 s；失败按「网络不可达 / 业务失败」两级处理。

**API 一览（12 个端点）：**

| 方法 | 路径 | 功能 | 主要参数 |
| --- | --- | --- | --- |
| GET | /api/ping | 连通性测试 | — |
| POST | /api/register | 注册 | username,password,nickname |
| POST | /api/login | 登录 | username,password |
| POST | /api/change-password | 修改密码 | username,newPassword |
| POST | /api/records?username= | 打卡上云 | sportType,duration,calorie,createTime,remark |
| DELETE | /api/records/{id}?username= | 删除单条 | — |
| DELETE | /api/records?username= | 清空记录 | — |
| GET | /api/leaderboard?days=&limit= | 排行榜（days=0 为总榜） | days,limit |
| GET | /api/feed?username=&limit= | 好友动态流 | username,limit |
| POST | /api/records/{id}/like?username= | 点赞/取消（幂等） | — |
| POST | /api/follows?username= | 关注/取关（幂等） | followee |
| GET | /api/users/search?keyword=&username= | 用户搜索（含 following 状态） | keyword |
| GET | /api/follows/my?username= | 我的关注/粉丝 | — |

**数据同步策略（离线‑在线同步）：**

1. 打卡保存：先写本地 SQLite（事务成功即提示用户）→ 异步调用 `/api/records` 上云；上云失败仅提示「已保存本地」，不阻塞、不丢数据；
2. 启动同步：页面恢复时按 15 s 轮询拉取排行榜与动态流；下拉刷新可手动触发；
3. 冲突处理：服务端以自增主键为准，本地记录与云端为「追加」关系，天然规避写冲突。

## 三、数据库设计

### 3.1 客户端本地库（fitness_check_in.db，版本 4）

**user_info**：`id`(PK)、`username`(UNIQUE)、`password`(PBKDF2 哈希)、`nickname`、`avatar_path`、`create_time`

**sport_record**：`id`(PK)、`sport_type`、`duration`(秒)、`calorie`、`create_time`、`username`(多用户隔离)、`remark`

### 3.2 服务端库（fitness_server.db）

**users**：`id`(PK)、`username`(UNIQUE)、`password_hash`(salt$hash)、`nickname`、`create_time`

**sport_records**：`id`(PK)、`username`、`sport_type`、`duration`、`calorie`、`create_time`、`remark`

**likes**：`id`(PK)、`record_id`、`username`、`create_time`，唯一约束 `(record_id,username)` 保证点赞幂等

**follows**：`id`(PK)、`follower`、`followee`、`create_time`，唯一约束 `(follower,followee)` 保证关注幂等

## 四、关键技术方案与多方案比对

### 4.1 服务端框架选型

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| Spring Boot | 生态完整、企业主流 | 依赖重、启动慢、配置复杂，课程演示讲解成本高 | ✗ |
| **Javalin 6（选定）** | 轻量（启动 <1 s）、API 简洁、REST 语义清晰 | 无全家桶，需自行组织分层 | ✓ |
| JDK HttpServer 手写 | 零依赖、完全可控 | 需自造路由/JSON/异常处理，易引入缺陷 | ✗ |

**选择理由**：课程项目的核心是「讲清楚协议与架构」，Javalin 以最小抽象暴露 HTTP 语义，便于答辩逐层讲解，同时保留成熟的序列化（Jackson）与异步能力。

### 4.2 客户端网络层选型

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| Retrofit/OkHttp | 生态成熟、注解式声明 | 引入多层依赖，学生难以解释底层 | ✗ |
| **HttpURLConnection + org.json（选定）** | Android 内置零依赖、协议细节透明 | 需手写线程调度与解析封装 | ✓ |

**选择理由**：零新增依赖使工程可信、体积小；手写 `ApiClient`（后台线程池 + 主线程回调）恰好是「网络编程」能力的直接体现。

### 4.3 服务端数据库选型

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| MySQL | 生产标准、并发强 | 需安装服务、账号配置，演示环境成本高 | ✗ |
| **SQLite（选定）** | 零安装、单文件、与客户端技术同源 | 并发写有限（课程规模足够） | ✓ |

### 4.4 通信与实时性方案

| 方案 | 实时性 | 复杂度 | 结论 |
| --- | --- | --- | --- |
| **REST + 主动轮询/下拉刷新（选定）** | 近实时（15 s 轮询） | 低 | ✓ |
| WebSocket 推送 | 强实时 | 高（连接管理、心跳、重连） | 备选（生产升级方向） |
| 自定义 TCP 协议 | 可控 | 需自定帧格式与粘包处理 | ✗ |

**选择理由**：社交动态与排行榜对实时性要求为「秒级至分钟级」，15 s 轮询 + 手动刷新已满足体验；REST 无状态特性使服务端实现与联调更可控。

### 4.5 密码安全方案

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| 明文存储 | 不可接受（此前版本缺陷） | ✗ |
| MD5/SHA-1 单次哈希 | 可被彩虹表破解 | ✗ |
| **PBKDF2WithHmacSHA256 + 随机盐（选定）** | JDK 内置、可调迭代次数、抗彩虹表 | ✓ |

### 4.6 UI 动画方案

| 方案 | 体积 | 效果 | 结论 |
| --- | --- | --- | --- |
| GIF/帧序列 | 大（MB 级） | 分辨率固定、易糊 | ✗ |
| 属性动画手写 | 小 | 表现力有限 | ✗ |
| **Lottie（Airbnb 开源，选定）** | 小（JSON KB 级） | 矢量、任意缩放、设计师工作流 | ✓ |

**创新点：**

1. **离线优先的打卡同步**：本地事务成功即反馈，网络同步异步化，弱网/断网零丢失；
2. **零依赖网络层**：内置 API 手写 REST 封装，协议链路完全可解释、可测试；
3. **轻量社交闭环**：在无 WebSocket 的前提下以「轮询 + 刷新节流」实现近实时体验，兼顾性能与实现复杂度；
4. **Lottie 情感化交互**：以矢量动画强化打卡成功的正向反馈。

## 七、核心算法与流程

### 7.1 连续打卡天数

按用户记录集合构建日期 Set；从今天起逐日回溯，命中则计数、未命中则终止。时间复杂度 O(连续天数)。

### 7.2 卡路里估算

`calorie = duration(秒) / 2`（轻量估算模型，满足记录与对比需求）；种子数据采用真实量级（如 30 min 跑步 ≈ 300 kcal）提升展示可信度。

### 7.3 排行榜聚合（服务端）

```sql
SELECT u.username, u.nickname,
       COUNT(r.id) AS check_in_count,
       SUM(r.duration) AS total_duration,
       SUM(r.calorie) AS total_calorie
FROM users u LEFT JOIN sport_records r
  ON r.username = u.username AND r.create_time >= datetime('now','localtime','-7 days')
GROUP BY u.username HAVING check_in_count > 0
ORDER BY total_duration DESC LIMIT ?;
```

「本周榜」与「总榜」通过同一 SQL 的时间窗参数切换，保证口径一致。

### 7.4 好友动态流

```sql
SELECT r.*, u.nickname,
       (SELECT COUNT(*) FROM likes l WHERE l.record_id = r.id) AS like_count,
       EXISTS(SELECT 1 FROM likes l2 WHERE l2.record_id = r.id AND l2.username = ?) AS liked_by_me
FROM sport_records r JOIN users u ON u.username = r.username
WHERE r.username = ? OR r.username IN (SELECT followee FROM follows WHERE follower = ?)
ORDER BY r.id DESC LIMIT ?;
```

### 7.5 离线同步流程

```
用户保存打卡 → 本地 SQLite 事务写入成功（立即反馈）
            → 异步 POST /api/records（后台线程）
                ├─ 成功：云端入库（动态/排行榜可见）
                └─ 失败：仅提示「已保存本地」，下次操作/刷新不丢数据
```
